# CarBridge 产品与技术规格

版本：0.1；日期：2026-10-01；实施更新：2026-10-02；基线：DiPlay 0.2.8。本文定义目标行为；本机实施已完成，证据及实车未验收边界见 [实施状态](IMPLEMENTATION_STATUS.md)。改造前事实见 [源码核对记录](CARBRIDGE_SOURCE_AUDIT.md)。

## 1. 范围与术语

首要目标是用户的吉利 ECARX Android 车机：已有日志记录为 Android 11 / API 30、型号 `999722 FX11-A2`；USB 盒子搭配参考 APK 的 F25 模式已由用户实测可方控。具体 ROM、iOS 和播放器版本仍须在联调报告中固定。

本项目以 `mobile` APK 为首个交付对象。`automotive` 是独立构建产物，不因目录名字包含 automotive 就视为本次目标；保留其可构建性，单独记录验证范围。

| 术语 | 定义 |
| --- | --- |
| 桥接模式 | CarBridge 发布 MediaSession；MediaBridge 显示/转发音乐信息并接受车机媒体控制，再控制 CarBridge |
| 直连模式 | CarBridge 自行注册 ECARX 媒体客户端，并处理车机回调；不依赖 MediaBridge 才能控制 |
| 路由所有者 | 对 CarBridge 这一播放来源，当前允许发布车机信息、处理车机媒体命令的一方 |
| 车辆媒体源所有者 | 车机此刻选中的应用，可能是 CarBridge、MediaBridge、收音机或其他音乐软件 |
| 主动播放 | 有证据的新播放意图，区别于持续播放状态和流重建；定义见第 5 节 |
| 注册 | SDK 客户端可用；不等于已申请播放或应当抢占其他音乐 |

MediaBridge 为其他播放器服务时可以继续注册。所谓“单一所有者”不是要求整台车只存在一个媒体客户端，而是禁止它与 CarBridge 同时替同一个 CarBridge 会话申请播放、发布歌曲和处理方控。

## 3. 模式与设置

### 3.1 设置入口

在 CarBridge 增加“车机适配”和“媒体接入方式”：

- 车机适配：`吉利 / ECARX`、`通用 Android`、`BYD`。本项目面向该车的首次安装默认吉利；允许切换，不能靠厂商字符串猜测就启动专用服务。
- 媒体接入方式：`自动（跟随 MediaBridge）`、`MediaBridge 桥接`、`ECARX 直连`。新安装默认自动。
- 状态：例如“正在通过 MediaBridge 桥接”“ECARX 直连待播放”“等待 MediaBridge 解除忽略”“车机服务不可用”。显示实际状态，不只显示保存的偏好。
- 音乐互斥：默认开启，说明为“后播放的音乐优先”；关闭作为兼容选项，明确关闭后不保证互斥。该设置同时控制统一音乐管理器，不能留一处绕过它偷偷申请焦点。

### 3.2 配套新版的决策表

以下以 iPhone 已连接、车型支持直连为前提；没有连接时可协商路由但不申请播放。

| CarBridge 偏好 | MediaBridge 状态 | 实际目标 |
| --- | --- | --- |
| 自动 | 已配对、未忽略 CarBridge、桥接就绪 | 桥接 |
| 自动 | 已配对、已忽略 CarBridge | 直连；先确认旧桥接路由停止 |
| 自动 | 未安装 MediaBridge | 直连；若 SDK 不可用则显示不可用 |
| 自动 | 新版明确报告停用且已完成退出 | 直连；必须获得退出确认 |
| 自动 | 已安装但失联、权限不足、SDK 不就绪或策略未知 | 等待/故障；不能仅凭超时启用第二条路线 |
| 桥接 | 未忽略、已配对且就绪 | 桥接 |
| 桥接 | 已忽略 | 等待解除忽略，保留该忽略选择，不暗改名单 |
| 桥接 | 未安装、旧版未完成手动配置、权限不足 | 等待配置，不静默直连 |
| 直连 | 配套新版可通信 | 协商直连；MediaBridge 对 CarBridge 临时排除桥接，忽略名单原值保留 |
| 直连 | MediaBridge 未安装 | 直连 |
| 直连 | 旧版或不可通信且可能仍在桥接 | 需要手动保证忽略/停用并验证，不能冒险双开 |

“桥接就绪”同时包含启用、所需授权、监听服务连接、车机后端注册及协作协议就绪。它不是“MediaBridge 已安装”或“当前有某个 PLAYING 会话”。

正常使用只需一个控制入口：选择自动后，在 MediaBridge 中忽略/取消忽略 **CarBridge 的新包名** 即可切换；选择明确直连后由协议让 MediaBridge 暂时绕过 CarBridge。明确桥接与已有忽略策略冲突时提示冲突，不能悄悄推翻忽略名单。旧 DiPlay 与 CarBridge 是不同应用，忽略旧包名不会自动作用于新包名。

### 3.3 交接与重启

交接采用“旧所有者停止 → 确認无旧输出/命令在途 → 新所有者提交 → 发布快照”的顺序。每轮带进程实例和递增代次；异步回调、封面结果、方控命令必须校验代次。模式切换本身不构成主动播放，不能使另一正在播放的软件被抢占。

如果 CarBridge 正在播放且仍拥有有效播放资格，可在交接时转移该资格并短暂静音；若交接期间用户选择了其他音乐，资格立即失效。默认不缓冲交接期间的方控，反馈“切换中”并丢弃，避免稍后突然连跳。

未知所有权进入等待状态，关闭冲突的车机发布/方控路径；音乐互斥开启时也关闭无法确认资格的音乐输出。恢复依赖重新握手及车机状态核对，不依赖固定等待后强行接管。详细约束见 [协作协议](MEDIABRIDGE_INTEROP.md)。

## 4. 歌曲信息与媒体小窗

### 4.1 统一状态

新增与车型无关的 `NowPlayingSnapshot` 和串行状态存储，至少包括：

| 字段组 | 内容 |
| --- | --- |
| 生命周期 | `connectionId`、`trackGeneration`、`revision`、接收时间 |
| 曲目信息 | 协议曲目 ID（如果存在）、歌名、歌手、专辑、时长 |
| 播放 | 播放/暂停/停止/缓冲/未知，播放速率，基准进度，单调时钟时间戳 |
| 资源 | 封面键与可读 URI，歌词资源/状态，来源为 native/cache/online/none |
| 能力 | 可执行的媒体动作；没有实现的 seek、收藏等不对外宣称支持 |
| 质量 | 字段是否已知、资源匹配置信度、错误原因；未知与空字符串分开 |

iAP2 更新是增量：同一曲目未出现的字段保留；明确清空应清空；确定换曲时先隔离上一首的资源；无法确认的曲目 ID/字段必须在协议探针阶段核实。仅凭标题相同不能判定是同一曲目。不能把每个增量帧都当作新歌曲。

播放进度只在真实播放时按单调时钟外推，暂停后冻结，跳转后更新基准，限制在有效时长内。缺少可信进度时发布未知，不用音频包数量伪造绝对进度。断开后清除会话和资源；播放未确认时不得先发布假 PLAYING 以抢方控。

### 4.2 Android MediaSession 与通知

`CarPlayMediaKeys` 的输入能力保留并接入新的命令路由；元数据输出改由统一快照驱动，补全标题、作者、专辑、时长、封面和播放状态。活动会话生命周期跟随连接及媒体可控性，不再靠 PCM 流存在与否独立推断播放状态。

通知可显示当前歌曲及播放器控制，使用同一快照；无歌曲时显示连接状态。暂停后保留可恢复的会话，断开释放。MediaSession 活跃本身不获得抢播资格。

直连模式也保留标准媒体会话供系统显示，但新版 MediaBridge 必须按协商结果排除它；避免通过隐藏会话解决抢控而破坏系统控制。

### 4.3 封面

优先级为 iPhone 原生封面 → 同曲目缓存 → 可选在线精确匹配 → CarBridge 占位图。现有代码只有文件传输 session 声明，原生封面尚需贯通链路、分片重组和曲目关联，不能仅新增 `setMetadata()` 就宣称完成。

原生通道设定资源大小/图片像素/并发/超时上限，失败不阻塞音频；迟到结果按连接与曲目代次丢弃。跨应用通过受控 `content://` URI/读取授权提供图片，MediaBridge 和 ECARX 服务进程的实际读取分别验证，不能发送仅本进程可访问的文件路径。小尺寸位图仅在 Binder 大小预算内使用。

桥接时由 MediaBridge 使用自己的封面补全能力；直连时 CarBridge 使用独立的资源解析模块。直连不得要求后台安装 MediaBridge 才能获得在线补全。避免同一模式下两端重复请求资源。

### 4.4 歌词

不把“iPhone 屏幕有歌词”当成 CarPlay 会传歌词的证据。若协议确实提供可用歌词，保留结构化数据；否则以歌名、歌手、专辑、时长匹配同步歌词并缓存。

桥接模式复用 MediaBridge 已有歌词查找、偏移和小窗渲染；CarBridge 负责提供可靠元数据与进度。直连模式按车机能力发布当前歌词行，可共享可独立运行的解析/缓存模块，但不把歌词塞入歌名伪装元数据。

在线匹配需处理现场版、伴奏、重名曲、不同语言、超时、断网和限流。置信度不足或只有纯文本时明确降级，不伪造滚动时间轴。已缓存资源离线可用；无资源时“暂无歌词”，不保留上一首歌词。

完整功能的验收必须涵盖可匹配曲目的封面和滚动歌词；所有歌曲均有资源不作为不切实际的保证。原生 iPhone 封面作为单独能力跟踪，未验证时不得标为已支持。

## 5. 音乐互斥与后一次主动播放

### 5.1 单一音乐管理器

新增统一播放仲裁器，合并 `AndroidMediaSink` 与 `CarPlayMediaKeys` 重复的音乐焦点申请。音乐输出需同时满足有效播放意图、Android 焦点允许、所选车机路线允许，以及当前连接有效。

ECARX 的 `requestPlay` 与 Android `requestAudioFocus` 不是同一件事：前者选择车机来源，后者请求系统音频协调，两者结果都需要处理。普通 Android 11 应用无法强制全系统任意不守焦点的软件停止；本项目保证自己的音乐及时让位，并对目标车机的可协调播放器实现互斥，实测不合作的软件列为兼容问题。

### 5.2 主动播放的证据与排序

| 输入 | 是否形成新播放意图 |
| --- | --- |
| CarBridge 界面点击播放、路由到本应用的明确方控播放、MediaSession `onPlay()` | 是，先生成意图再申请资格 |
| 已确认暂停后的 iPhone 新 PAUSED → PLAYING 变化 | 可作为手机侧播放意图；需排除自身恢复、旧会话和迟到事件 |
| 手机已 PLAYING 时再次点击播放但协议没有区别事件 | 不能凭空辨认，列为探针验证限制；依赖明确事件或先暂停再播放 |
| 初始连接快照、断线重连初始 PLAYING、流重建 | 否；互斥开启时需新的有效意图才抢占 |
| 自动换曲、持续 PLAYING、进度/标题/封面更新 | 否；可以延续未失效的播放资格 |
| 下一曲/上一曲 | 执行命令；只有当前已获资格或确认造成新的主动播放时才延续/申请，不能后台借切歌抢占 |
| 本项目为临时恢复发出的 PLAY | 延续原意图，不新增优先级 |
| 另一车机音乐源开始播放/获得车机控制 | 当前 CarBridge 意图失效或被覆盖，不通过轮询反抢 |

排序使用本机单调时钟、来源、连接代次、递增事件序列，手机墙上时间不参与先后比较。记录主动、推断和自动恢复三种来源。不能仅用“最后收到 PLAYING 的应用”作为最后主动播放应用。

失焦后立即发送一次明确 PAUSE 并等待状态反馈，配合本地门控防止手机继续响；在暂停确认前收到的重复 PLAYING 不重新抢占。若之后始终无法辨认手机端新意图，保持让位并显示可用的明确恢复入口，不反复夺取焦点。

### 5.3 状态与动作

| 事件 | 必须动作 |
| --- | --- |
| 只连接手机 | 建立会话/订阅；不抢焦点，不调用车机 requestPlay |
| 有效播放意图 | 协商路线、申请车机资格与音乐焦点；成功前音乐门关闭 |
| 焦点拒绝/延迟 | 保持门关闭，不以流启动绕过；获准回调也需意图未被覆盖 |
| 永久失焦/其他音乐源接管 | 立即门控并暂停/清理旧音乐缓冲，向 iPhone 发 PAUSE，失效旧资格；不停止整条 CarPlay 连接 |
| 用户暂停 | 门关闭、同步状态、释放音乐焦点/活跃播放资格，保留可操作媒体会话 |
| 临时失焦 | 暂停音乐并记录可恢复令牌；恢复前检查仍是同一连接、意图且没有更晚的用户选择 |
| 可压低的导航提示 | 按音频通道和策略压低音乐，提示结束仅恢复音量，不产生新播放意图 |
| 断开/控制器更换 | 释放焦点、路由资格与缓冲；所有旧回调失效 |

门控覆盖首次 `AudioTrack.play()`、补缓冲重启、尾部排空及所有恢复路径；门关闭时不能因队列增大再次开播。保持必要的协议接收，丢弃过期音乐，避免恢复时播放几秒旧内容。

### 5.4 通话、Siri、导航

音乐互斥不等于整个应用所有音频独占。通话/通信优先于音乐，Siri 与导航按用途管理；不得继续使用“音乐比电话优先”的内部比较来统一裁决。临时提示不切歌曲所有权；通话结束仅在原音乐没有被后来意图取代时恢复。驻车视频保留上游单独控制优先级及安全限制。

## 6. ECARX 直连与方控

以参考 APK 的 F25 使用 EAS 媒体中心注册/回调路径为依据，优先提炼 MediaBridge 已在目标车工作过的 SDK 适配经验。F25 是参考 APK 的模式名，不是通用 Android 方控开关；当前 MediaBridge 实际后端为标准/legacy，不能把旧枚举存在解释为已启用 F25。

客户端以 CarBridge 实际安装包名注册，能力探测后选择兼容注册方法。日志记录服务、版本、注册方法、token 有效性、来源类型及焦点结果；未知 ROM 不循环暴力重试。禁止冒用 `com.flyme.auto.energy`、硬编码 QQ 音乐启动 Intent 或伪造封面 URI。

| ECARX 回调 | CarBridge 语义 | 最终路径 |
| --- | --- | --- |
| onNext / onPrevious | NEXT / PREVIOUS | 统一命令路由 → `CarPlayController.sendMediaButton` → CarPlay HID |
| onPlay / onPause | PLAY / PAUSE，保留明确语义 | 同上，播放经仲裁，暂停可撤销本应用播放 |
| toggle | PLAY_PAUSE | 仅真实切换指令使用 |

参考盒子的 203/204/205 是其 USB 协议数值，不能移植到 CarPlay HID。BYD 的 353 键及将硬件 PLAY/PAUSE 合并为 toggle 的兼容规则只保留在 BYD 配置；吉利明确回调不采用该规则。

输入选择优先通过路由所有权禁止重复路径。存在 Android 与 ECARX 双重转发时按事件标识、来源和语义关联去重，不以过大的时间窗口吞掉用户快速连续切歌。无事件 ID 的 SDK 回调需车机采样后确定规则。`sent=true` 仅表示命令提交；最终效果由 iPhone 状态、曲目变化及实际观察佐证。

媒体上下曲与 Siri、音量是不同通路。本轮必须交付媒体控制；音量保留系统行为，Siri 的吉利专用键是否可达单独验证，不能因为媒体回调可用就承诺语音键可用。

## 7. 车型隔离与 Geely 按钮

用 `VehicleProfile` 汇总媒体适配、OEM 显示默认值和车辆专用能力。既有 BYD HUD、仪表、导航、定位、按键与驻车功能保留在对应适配中；Geely 不启动其 ADB/广播/服务，也不通过伪造 BYD 状态开启受限视频。

Geely OEM 图标取 [用户原图](assets/carbridge/geely-logo-reference.png) 上方的深色车标，去除底部中英文文字。制作纯黑标志、方形画布的 PNG，保持比例、居中留白；默认白底保证黑标在 CarPlay 深色界面可辨认。不要把宽车标拉伸成方形。具体像素尺寸按现有协议验证后固定，保留原图及加工说明。

标签默认 `Geely`，不把项目应用名称改成 Geely。应用显示名称为 `CarBridge`。设置预览与实际发送的默认图标使用同一资源入口，修正上游预览与发送采用不同资源的情况。

已有用户自定义 OEM 标签/图标优先保留；新安装和“恢复车型默认”使用 Geely。若将来导入旧设置，无法区分 BYD 默认值和用户刻意设置时不得静默覆盖。修改后可能需要重新连接 iPhone，缓存问题通过正常重连/重新配对排查，不能为刷新图标改写认证身份。

点击 OEM 图标沿用 Android HOME 路由，CarPlay 在后台保留；与携带视频 URL 的 `requestUI` 分支区分，不破坏上游驻车视频功能。

## 8. 可维护性、边界与完成定义

建议新增模块/包边界：`nowplaying`（协议状态）、`playback`（仲裁与命令）、`vehicle`（车型与 ECARX）、`interop`（MediaBridge 协议）、`artwork/lyrics`（资源）。名称为设计落点，不代表当前已存在。

应用 ID 规划为 `io.github.rhsr1024.carbridge`，调试后缀 `.debug`；首次发布前在 P01 固定。保留内部 `com.shilapi.xcertplay` 命名空间以减少上游冲突。新身份允许与 DiPlay 并存，不能继承旧应用私有配置和系统授权；Provider authority、Intent、包可见性、签名和 MediaBridge 忽略条目必须随之更新。

完成必须同时满足桥接与直连、互斥与让位、歌曲卡片与资源降级、Geely 按钮、旧版兼容、升级恢复及目标车机验收。单独编译成功、SDK 注册成功或收到 NEXT 日志均不是完整交付。任务与验收关联见 [实施计划](CARBRIDGE_IMPLEMENTATION_PLAN.md) 和 [验证方案](CARBRIDGE_VALIDATION.md)。
