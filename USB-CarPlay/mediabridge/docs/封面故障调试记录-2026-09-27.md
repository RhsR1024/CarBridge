# MediaBridge 封面故障调试与决策记录

日期：2026-09-27（Asia/Shanghai）
最终实车版本：`2.0.2-Bridge-26092709`（versionCode `26092709`）

## 1. 最终结论

用户已在目标车实测确认 26092709：

- 标准 MediaCenter 桥接正常；
- 方向盘媒体控制正常；
- 封面正常显示；
- 歌词正常显示。

本次问题不是 ADB 关闭或车机重启导致的封面读取权限丢失。26092708 的实车日志证明，车机已经拿到桥接返回的封面 URI，并由 MediaCenter 进程成功打开了对应 PNG；真正的问题位于“播放器封面候选选择、图片兼容处理和完整媒体状态重复发布”这一段。

最终采用的组合修复为：恢复 1.8 的播放器原始 URI 透传兜底、把过小的内嵌缩略图规范为车机更稳定的尺寸、同曲不向更小候选倒退，并在输出端忽略只有播放进度变化的完整状态重发。

## 3. 关键日志如何排除错误方向

26092708 的日志出现了三组决定性证据：

1. `get_artwork` 持续返回非空 URI 和 UUID，说明桥接 Binder 已把封面字段交给车机；
2. MediaCenter 调用 `open_file` 时记录为 `exists=true`，并读取到 3～10 KB 左右的 PNG，说明 ContentProvider、临时 URI 授权和文件本身都可访问；
3. 同一首歌的候选封面在 `70x70`、`129x129` 等尺寸之间切换，车机每几百毫秒重复查询相同或交替的 UUID。

因此排除了以下假设：

- ADB 关闭造成封面权限丢失；
- 通知读取授权在重启后失效；
- artwork authority 或 URI grant 错误；
- MediaCenter 没有调用 `getArtwork()`；
- 车机拿到 URI 后无法打开文件。

日志中的 `Missing permission to control media` 来自系统 active-session 枚举接口，但通知监听 token 回退随后成功发现酷我会话并持续输出元数据，因此它不是本次无封面的原因。不能仅看到这条异常就要求用户重新开放 ADB 或增加系统权限。

诊断日志导出也没有失效。车机没有可处理 `ACTION_CREATE_DOCUMENT` 的文件选择器，所以“选择其他位置”会抛出 `ActivityNotFoundException`；程序随后正常回退到公共 `Download/MediaBridge`，用户提供的日志文件正是该回退路径的产物。

## 4. 参考实现的真实差异

### 4.1 1.8 参考

对 1.8 实际 DEX 的核验得到以下事实：

- 封面字段优先级是 `ALBUM_ART_URI → ART_URI`、`ALBUM_ART → ART`；
- `LegacyMusicClient` 保留同一个 `MusicPlaybackInfo` 对象，并在元数据、进度和歌词变化时原地修改；
- 播放器给出非空封面 URI 时，桥接进程即使无法自行读取，也会保留该原始 URI，让具有更高权限的 MediaCenter 尝试读取；
- 缓存图片使用 PNG，并通过 `com.netease.cloudmusic.iot.artwork` authority 提供。

这意味着“桥接进程读不到播放器 URI”不等于“车机也读不到”。26092708 把这种 URI 换成了内嵌小图，反而丢失了 1.8 的有效兜底。

### 4.2 v3 反编译参考

v3 的媒体监听输入层仍会频繁发送更新，但服务输出层会比较标题、歌手、播放状态和封面 URI 等车机可见字段；只有进度变化时，不会重新提交整份媒体状态。它证明输出端去重是原版体系中的兼容策略，不应把进度 ticker 等同于封面/元数据更新。

v3 的部分版本偏向 `ART/ART_URI`，而 1.8 偏向 `ALBUM_ART/ALBUM_ART_URI`。实测说明字段顺序本身不是唯一根因，因此最终没有继续在这两个顺序之间盲目切换，而是保留已核实的 1.8 顺序，并修复 URI 兜底与图片稳定性。

## 6. 26092709 的最终实现决策

### 6.1 原始 URI 透传

`ArtworkRepository` 仍优先尝试把本地可读 URI 重新缓存到自己的 provider；如果播放器 URI 非空但桥接进程无法读取，则不再立即换成 Bitmap 或通知缩略图，而是原样返回该 URI。这与 1.8 的有效行为一致，并利用 MediaCenter 的特权读取能力。

诊断日志新增 `source_uri_passthrough`，只记录 scheme，不记录完整 URI。

### 6.2 小图规范化与同曲质量单调性

日志里的 70×70、129×129 PNG 虽能被打开，但 ECARX 2.5.0 界面仍显示空白唱片占位。因此：

- 最长边小于 256 像素的图片放大到最长边 512 像素；
- 最长边超过 512 像素的图片按比例缩小；
- 256～512 像素的普通封面保持不变；
- 同一 track identity 已有较大候选时，不接受后续更小候选覆盖；
- fingerprint 路径只缩小、不放大，避免高频媒体回调反复分配 512 像素 Bitmap。

### 6.3 输出端可见状态去重

`LegacyBackend` 的完整状态键包含播放器、曲目标识、标题、歌手、专辑、封面 URI、时长、播放状态、收藏、播放器歌词和显示开关，不包含不断变化的当前位置和时间戳。

- 车机可见状态变化时调用 `updateMusicPlaybackState`；
- 只有进度变化时继续调用 `updateCurrentProgress`；
- 当前歌词变化时继续调用 `updateCurrentLyric`；
- 歌词内容重新获取等明确场景可强制刷新完整状态。

这样既保留实时进度和歌词，又停止同一封面 UUID 每几百毫秒被重新提交和打开。

### 6.4 保留 1.8 对象生命周期

`LegacyMusicClient` 继续持有一个 final `MusicPlaybackInfo`，所有更新原地写入。没有采用 26092707 中“每次生成新对象”的试验方案，避免 Binder 并发读取时对象身份和 1.8 不一致。

### 6.5 诊断导出

“保存到下载目录”作为默认按钮，直接写入 `Download/MediaBridge`；“选择其他位置”保留为可选项，若 ROM 没有文件选择器则自动回退到 Downloads。该流程已由本次用户提供日志实际验证。

## 8. 后续排查准则

如果未来某个播放器再次不显示封面，按以下顺序判断，不要先修改权限或字段顺序：

1. 确认当前 track identity、播放器包名和桥接注册状态；
2. 检查 `resolve_candidates`：播放器给了 URI、Bitmap 还是通知 Icon；
3. 检查是否出现 `source_uri_passthrough` 或 `cache_ready`，以及源尺寸和输出尺寸；
4. 检查 `get_artwork` 是否返回非空 URI；
5. 检查 `open_file` 是否出现、文件是否存在、字节数是否稳定；
6. 只有 provider 未被打开时才继续查授权/authority；已经成功打开时应查图片内容、尺寸、编码和发布频率；
7. 区分标准 MediaCenter 与 F25 路径，不能把当前标准通道的实车结论外推到尚未单独验收的车型和后端。

本记录把 26092709 作为当前目标车/酷我环境的已验证基线。后续封面相关改动应保留上述探针和回归测试，并与该 APK 做覆盖安装和实车对照。

## 9. V3 封面对齐复查（26092712）

用户随后提供了 `mediabridge-probe-20260927-132304-572.log.txt`，并反馈当前版本在 LX Music、酷我有封面，但酷狗概念版和汽水音乐没有；同一车机上的 `MediaBridge for Flymeauto V3_sign.apk` 可以显示四类播放器封面。

### 9.1 新日志排除的方向

这份日志已经记录到酷狗概念版 `com.kugou.android.lite` 和汽水会话 `com.luna.music.car` 的完整读取链路：

- 酷狗出现 `240x240` 位图，随后生成 `512x512` PNG；
- 汽水出现 `426x426` 位图，随后生成 `426x426` PNG；
- 两者都出现 `open_file exists=true` 和非零字节数；
- `get_artwork` 返回非空 URI，MediaCenter 进程实际打开了缓存文件。

因此本轮仍不能把“ADB 关闭/车机重启后权限丢失”作为根因。日志中的 `Missing permission to control media` 是 active-session 枚举权限不足；通知监听 token 仍成功发现播放器，且 artwork provider 已被打开，和封面文件无法访问不是同一个故障。

### 9.2 V3 DEX 与当前实现的封面差异

对 `D:\CarSoft\MediaBridgeApp\MediaBridge for Flymeauto V3_sign.apk` 的 `classes.dex` 反编译核验得到：

1. V3 在没有可用覆盖 URI 时读取 `android.media.metadata.ART`，只有为空才回退 `ALBUM_ART`；URI 顺序也是 `ART_URI` 后 `ALBUM_ART_URI`。
2. 当前版本此前采用 `ALBUM_ART`、`ALBUM_ART_URI` 优先。这会让同时提供两套候选的播放器把专辑缩略图送给车机，而不是当前歌曲封面。
3. V3 的 `UniversalBridgeService` 维护标题、歌手、状态、封面 URI 的可见状态去重；当前 `LegacyBackend` 已用完整状态键实现同等输出去重。
4. V3 有 `CoverFallback`，在完全没有 artwork 时按标题/歌手向 NetEase、QQMusic 查询；当前 `ArtworkRepository` 已有同样的在线来源，且在线检索默认开启。
5. V3 声明能力 `[0,2,3]`，本探针版额外声明 `[0,1,2,3]`；V3 清单还包含系统级 `MEDIA_CONTENT_CONTROL` 等权限。由于本次日志已经证明当前版本获得并打开了 artwork 文件，能力数组和系统权限暂不改动，以免回归已经正常的方控和桥接。

## 9.4 远程 URI 与内嵌位图路径对齐

后续复测仍表现为酷我、LX Music 有封面而酷狗概念版、汽水音乐无封面时，重新对照 V3 DEX 和 26092711 日志发现输出层还有一个顺序差异：当前实现只要存在 `http/https` URI 就立即透传，导致酷狗/汽水同时提供的 `ART/ALBUM_ART` 位图没有进入本地缓存。V3 的兼容路径应为：

- 远程 URI 与内嵌位图同时存在：优先缓存当前歌曲位图并返回受限 provider URI；
- 只有远程 URI、没有可用位图：保留原始 URI 透传，兼容酷我这类会话；
- 本地 URI：先尝试进程内读取，失败后再按同一顺序回退。

已在 `ArtworkRepository` 落地该顺序，并增加“远程 URI + 240x240 内嵌位图必须生成 content URI”的回归测试。该修复不改变 V3 的 `ART_URI/ART` 优先级，也不改变已有的 UUID/输出去重逻辑；仍需签名后在四个播放器上复测。

## 9.8 实车截图复核：稳定来源后再完整缩放（26092717）

26092716 实车截图揭示，单纯对最终 Bitmap 做 `1/√2` 缩放仍不充分：图四虽然出现了安全区方块和柔化背景，但方块内部已经是局部画面；程序只能缩小收到的像素，不能恢复进入桥接前已经丢失的内容。图一和图三也显示播放器原生界面与桥接圆窗的取景范围明显不同。用户明确目标为“把完整原图压缩到正常显示大小”，而不是裁剪或缩小局部图。
